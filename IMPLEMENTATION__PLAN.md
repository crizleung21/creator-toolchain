# Creator Toolchain — IMPLEMENTATION PLAN

**Repository:** `crizleung21/creator-toolchain`  
**Plan status:** Approved for execution  
**Scope:** P0 + P1  
**Roadmap:** P2 only  
**Target state schema:** `0.4.0`  
**Architecture constraint:** Preserve the existing seven-skill architecture  
**Core-skill constraint:** Do not add an eighth core skill  
**Implementation strategy:** Add deterministic support scripts beneath the seven skills  
**Recommended release target:** Creator Toolchain `v1.1.0`

---

## 1. Executive Summary

Creator Toolchain already has a strong packaging and validation foundation: seven authoritative Codex skills, a generated byte-equivalent plugin mirror, deterministic package inventory, reproducible ZIP creation, repository/state/plugin validators, unit tests, and stored behavior-acceptance evidence.

The remaining gap is **execution completeness**. The current implementation is primarily an instruction-driven skill suite. This plan converts it into a deterministic, testable workflow system that can:

1. bootstrap a fresh repository;
2. create a complete typed plan;
3. approve and execute that plan;
4. verify task-level acceptance criteria;
5. reconcile planned versus actual work;
6. append immutable ledger evidence;
7. update state atomically;
8. stage and approve rules safely;
9. recover from interrupted or failed workflows;
10. rerun behavior acceptance and writable end-to-end tests against the current commit and package.

The seven existing skills remain the workflow owners. New Python modules, JSON Schemas, templates, and test runners provide deterministic execution support; they do not constitute an eighth skill.

## 3. Objectives and Success Definition

### 3.1 Required Core Loop

```text
BOOTSTRAP
→ INTAKE
→ PLAN QUALITY GATE
→ APPROVAL
→ EXECUTION
→ VERIFICATION
→ RECONCILIATION
→ LEDGER APPEND
→ STATE UPDATE
→ RULE PREFLIGHT / PROPOSAL
→ HEALTH CHECK
→ AUDIT / REMEDIATION HANDOFF
```

### 3.2 Core Function Complete

Creator Toolchain is **Core Function Complete** only when:

- a fresh repository can be initialized safely and idempotently;
- every declared state surface validates against schema `0.4.0`;
- intake creates the complete planning artifact set;
- approved plans execute through a deterministic lifecycle;
- every task has observable verification evidence;
- reconciliation and ledger closure are mandatory;
- state mutations are atomic and recoverable;
- rule proposals cannot auto-promote;
- all declared rule domains exist or are removed from capability claims;
- behavior acceptance is rerunnable;
- at least one writable golden workflow passes;
- the plugin installs and discovers exactly seven skills;
- release evidence is tied to the current commit and package hash.

---

## 4. Non-Goals

The implementation does **not** include:

- an eighth core skill;
- web or desktop UI;
- mandatory hooks;
- MCP servers;
- external SaaS integrations;
- telemetry enabled by default;
- full P2 productization;
- replacement of the repository-first state model;
- redesign of the seven-skill conceptual architecture.

## 5. Architecture Invariants

### 5.1 Seven Skills

| Skill | Responsibility |
|---|---|
| `creator-orchestrator` | Select one primary workflow and preserve explicit handoffs |
| `creator-intake-planner` | Convert raw ideas into typed, acceptance-driven plans |
| `creator-execution-cycle` | Execute accepted plans through Plan, Execute, Verify, Reconcile |
| `creator-workspace-manager` | Own repository-local workspace state and health |
| `creator-rule-router` | Select, stage, approve, reject, recall, and audit rules |
| `creator-skill-workbench` | Discover, scaffold, distill, score, and review skills |
| `creator-evidence-audit` | Produce evidence-backed findings and remediation handoffs |

### 5.2 Source and Mirror

```text
Authoritative source: .agents/skills/
Generated mirror:    plugin/creator-toolchain/skills/
```

The mirror must remain byte-equivalent to the authoritative source.

### 5.3 Ownership and Boundaries

- `creator-workspace-manager` owns all `.creator/*.json` surfaces except `.creator/rules.json`.
- `creator-rule-router` owns `.creator/rules.json`.
- `creator-evidence-audit` does not mutate its audit target.
- `creator-intake-planner` does not execute product work.
- `creator-execution-cycle` does not execute an unapproved plan.
- All durable state changes require deterministic validation and evidence.

# 11. Risk Register

| Risk | Level | Mitigation |
|---|---:|---|
| Schema migration corrupts state | High | Dry-run, backup, atomic write, rollback, fixtures |
| Routing regression | High | Precedence table and behavior cases |
| Scripts become a second architecture | High | Skills retain ownership; scripts are support only |
| Partial plugin mirror | High | Temporary mirror + atomic replacement |
| Behavior QA remains self-attested | High | Runner and evidence spans |
| False-green health | High | Derived health engine |
| Rule approval bypass | High | State machine and immutable approval record |
| Project-type scope expansion | Medium | Contracts only; no new runtime subsystem |
| Release process becomes slow | Medium | Fast checks separated from full release gates |
| Version divergence | Medium | One authoritative version source |
| Existing installation breaks | Medium | Migration and clean-install tests |
| Evidence is machine-specific | Medium | Repository-relative provenance |

# 12. Rollback Strategy

Each phase is independently revertible:

```text
RB-01 schema and migration
RB-02 intake artifacts
RB-03 execution lifecycle
RB-04 workspace health and reconciliation
RB-05 rule governance
RB-06 routing, Workbench, and Audit
RB-07 behavior and E2E QA
RB-08 release and CI
RB-09 documentation
```

Rollback when:

- state validation weakens;
- data loss occurs;
- invalid lifecycle transitions become reachable;
- routing selects the wrong primary workflow;
- mirror parity becomes nondeterministic;
- ZIP output becomes non-reproducible;
- behavior results lose evidence traceability;
- clean installation fails;
- migration cannot restore the source state.

Every state-changing command must support pre-write validation, backup, temporary write, post-write validation, restoration, and rollback ledger evidence.
